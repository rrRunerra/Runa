# Runa Encryption & Cryptographic Glossary

This glossary defines the core cryptographic and architectural terms used in Runa's encryption system.

---

## 1. Identity & Device Management

### Master Key (MK)
A symmetric key derived locally on a user's client device from their master passphrase using a key derivation function (e.g., Argon2id). It is used to encrypt/decrypt the user's private keys stored locally or in encrypted escrow.

### Recovery Key (via 2FA Backup Codes)
A key derived from a user's pre-existing multi-factor authentication (2FA) backup codes. This is used as an escrow decryption secret if the user loses their password, preventing permanent lockout from E2EE data.

### Device Linking Request
An interactive notification sent to active devices when a user logs in on a new device. Upon approval, an active device uses the new device's public key to securely transmit the encrypted master key bundle.

### Device Revocation
The process of deleting a registered device from the database, which invalidates its identity key, signed prekey, and prekey bundles, effectively terminating its session and capability to decrypt future messages.

### Identity Key (IK)
A long-term key pair representing a specific device's identity. 
* **Type:** Curve25519 (for key exchange) or Ed25519 (for signing).
* **Usage:** Public key is stored on the server to verify the device; private key remains secure on the device.

### Signed Prekey (SPK)
A medium-term key pair generated by a device, signed by its Identity Key, and uploaded to the server. It is rotated periodically.
* **Usage:** Used in the X3DH handshake to prevent man-in-the-middle attacks during offline session establishment.

### One-Time Prekey (OPK)
A bundle of short-lived key pairs generated by a device and uploaded to the server. The server dispenses them one-by-one to clients initiating sessions.
* **Usage:** Ensures cryptographic forward secrecy even when initiating a secure channel with an offline user.

## 2. Messaging

### X3DH (Extended Triple Diffie-Hellman)
A protocol for establishing a shared secret key between two parties who mutually authenticate each other using identity keys, even if one of the parties is offline at the time.

### Double Ratchet
A key management algorithm where parties derive new keys for every message using a combination of a Diffie-Hellman ratchet (based on active communication exchanges) and a symmetric KDF ratchet (based on message sequencing).
* **Property:** Provides both **Forward Secrecy** and **Break-in Recovery**.

### Message Fan-out
A simple approach for group messaging. Instead of generating group-wide symmetric ratchets, the sender's client encrypts the message individually for each participant's active devices using standard 1-to-1 Double Ratchet sessions.

## 3. Email & File Storage

### UserEmailAccount
A database entity representing an external SMTP/IMAP account linked to Runa. Users can link multiple accounts (Thunderbird style). It contains:
* **Identity settings:** Display name, organization, signature formatting, reply-to overrides, and visual color codes.
* **Connection parameters:** IMAP/SMTP hostnames, ports, and SSL/TLS security flags.
* **Encrypted credentials:** Passwords encrypted using reversible server-side encryption.

### Reversible Credential Encryption
The process of storing a user's external email passwords encrypted at rest in the database.
* **Algorithm:** AES-256-GCM.
* **Key Custody:** The encryption key is managed by the server (in environment configurations) so the backend service can decrypt the credentials to send/receive emails via SMTP/IMAP.

### File Encryption Key (FEK)
A random symmetric key (AES-256-GCM) generated client-side for encrypting a specific file or folder. Only created if the user manually marks a file or folder as "Encrypted" (E2EE).

### File Chunking
The process of splitting large files (>50MB) into smaller segments (chunks) prior to client-side encryption. Each chunk is encrypted and uploaded separately to prevent browser out-of-memory crashes.

### Hash Fragment Decryption
A zero-knowledge link sharing technique. The encryption key for a shared file is appended to the share link after the `#` character. Because browsers do not transmit the URL fragment to the server, visitors can load the client-side decryption app, download the encrypted file blob, and decrypt it locally without the server ever seeing the key.

### Background Email Synchronization
A scheduled background service in Runa that periodically connects to remote IMAP mail servers to fetch new email messages and sync changes (such as flag modifications or deletions) into the local database cache.

### Full Local Cache (Mail)
An archiving strategy where Runa downloads and stores all email envelope fields, message text/HTML bodies, and attachments in its local database. This guarantees that messages remain preserved and readable offline in Pegasus, even if they are deleted or purged from the remote email provider.

## 4. Notifications Engine

### Shared Notifications Package
The `@runa/notifications` package containing standard interface declarations, status types, payloads, and validation schemas used by both frontend and backend teams.

### Notification Gateway
A WebSocket Gateway endpoint integrated into NestJS that handles instant, bi-directional real-time communication, ensuring that alert updates and authorization prompts are pushed immediately to all connected browsers.
